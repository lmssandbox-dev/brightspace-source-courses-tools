# Shared org-code directory

Course Copy, Source Deployer and Date Manager now share a persistent org-code → ID directory in the app's existing MongoDB database. No new database, Redis service, CSV column or end-user control is required.

## What happens on upload

1. IDs without codes bypass code resolution entirely.
2. The app deduplicates supplied codes and queries MongoDB in batches of 500. Dataset records and confirmed Source Course creation overlays are combined by Org Unit ID, retaining lifecycle evidence and cross-type duplicate checks.
3. When directory evidence cannot safely resolve a code, the shared resolver calls `orgstructure/?exactOrgUnitCode=...` across supported org-unit types. It consumes complete pagination within 100 pages / 5,000 results and validates IDs, exact codes, and type information. A complete empty result means not found; HTTP 200 by itself is not a match. Multiple results are ambiguous. A single live result absent from the dataset can resolve with explicit `live-verified` lower-assurance provenance, including courses created directly in Brightspace before dataset synchronization. Known deleted or recycled evidence remains ineligible. Each job shares one promise per code; the existing eight mapping workers and shared API rate limits still apply.
4. Accepted live evidence, including complete empty results, is stored in `org_resolution_live` with its verification timestamp and provenance. Live snapshots expire after 15 minutes and must be rechecked; an authoritative dataset publication also supersedes earlier snapshots. Dataset synchronization remains the source of lifecycle truth and reconciles Source Course Creator overlays by ID. If both ID and code are supplied, the resolved ID must match. Ambiguous codes and mismatches are rejected, never guessed. Existing duplicate, self-copy and conflict checks remain.

Course Copy and Source Deployer exclude invalid rows and retain them in reports. Date Manager retains its existing requirement that all courses pass validation before application. Date Manager proceeds directly from identifier mapping to activity discovery, without course-detail or source-type requests. Source Deployer skips separate source/replica preflight checks; activation settings reads and read-back verification remain. Course Copy submissions and native result checks use eight workers; Source Deployer execution/checks also use eight; date updates remain at four. The directory does not grant API permissions or change submission/retry behavior.

## Nightly refresh

The running app checks whether a refresh is due at startup and every minute. The default schedule is **06:00 UTC (03:00 Brasília)**. A missed run is picked up when the service next starts; a sleeping or stopped server cannot run a timer. Configure the hour after your tenant's dataset generation window.

On first setup, the importer downloads the latest **Organizational Units** full extract and all available newer differentials, oldest first. Subsequent runs download only differentials not already committed. A newer full (or a reissued full) triggers a complete rebuild and resets the extract ledger. A directory representation version change also requires a full rebuild; older saved ledgers still enforce history continuity. Selection follows actual extract timestamps, independent of the customer’s release weekday or frequency. Existing installations without a usable ledger rebuild from a full extract, and cannot publish if known history would be lost. It publishes the generation atomically only after every file has been downloaded, parsed, validated and saved. Failed imports leave the previous generation usable and retry after one hour. A database lease prevents overlapping scheduled/manual imports across app instances. Restarted imports rebuild staging rather than publishing partial data. The committed extract ledger advances atomically with the published directory, so failed runs do not skip files on retry. Extract identities use schema/plugin, type, queued/created timestamps and version; signed download URLs are not persisted in the ledger. The published `asOf` value is the `QueuedForProcessingDate` of the newest extract included in that generation; it records dataset freshness, not the time the import finished.

Brightspace's dataset API supplies opaque extract/download links; the app follows those links rather than constructing filenames. It handles paginated metadata and signed HTTPS redirects. OAuth authorization is sent only to the initial tenant API URL, never to an external download host. See [D2L's dataset API](https://docs.valence.desire2learn.com/res/dataExport.html#brightspace-data-sets).

The importer validates every Organizational Units row, including numeric `OrgUnitTypeId`, and persists supported Course Offerings, Source Courses, Course Templates, and the configured standard Department by `OrgUnitId`, including compact lifecycle evidence for deleted and recycled records. The dataset's `Type` is a customizable type name and has no type-code field. Department identity comes only from equality between `OrgUnitTypeId` and `BS_STD_DEPARTMENT_TYPE_ID`; the original `Type` text is retained as `Type.Name` and may be renamed freely. Dataset-derived Department records have no `Type.Code`. The individual unit's `OrgUnitId`, `Code`, and `Name` map to `Identifier`, `Code`, and `Name`; `OrgUnitTypeId` maps to numeric `Type.Id`. Existing system course types retain their compatible `Type.Code` values. `IsDeleted=true` means deleted unless `RecycledDate` is populated, which classifies the record as recycled. A populated `DeletedDate` means deleted; a populated `RecycledDate` means recycled even when `IsDeleted=false`. Current requires `IsDeleted=false` and both date fields empty. Missing lifecycle values are unknown. `IsActive=false` alone does not affect lifecycle. Duplicate IDs are checked across every row in each extract. Full imports stage supported records with lifecycle evidence. Differential rows update evidence by ID and remove records only when they change to an unsupported type. These historical lifecycle records are used for duplicate discovery and are never eligible as current resolution results. See the [Organizational Units dataset field definitions](https://community.d2l.com/brightspace/kb/articles/4529-organizational-units-data-sets).

Imports reject missing required headers, duplicate IDs within an extract, incompatible dataset versions, missing initial full extracts, and invalid ZIP/CRC. There is no fixed 36-hour gap rule. Incremental updates require the last committed extract to remain in the available listing as a continuity checkpoint. If it has expired and newer files appear, the app waits for a suitable new full instead of guessing what was missed. Newly appearing older or same-time differentials also stop the import to avoid overwriting newer changes. This cannot detect every unpublished/missing file: the API provides no complete sequence guarantee, so tenant dataset availability still requires monitoring. No new dataset is generated by the app; it consumes published extracts.

## Freshness and isolation

Dataset and creation-overlay cache hits reflect the saved snapshot, not a live permission check. Lower-assurance live cache records are revalidated after 15 minutes, so an archived or renamed course cannot remain resolvable indefinitely from live evidence. ID+code matching uses the same shared resolver. Use IDs alone when identity must not depend on a mutable code. Changing permissions is still enforced by Brightspace when processing requests; directory membership is not an access grant.

Live lookups newer than the latest publication can fill gaps for recently created or renamed units. The next successful authoritative publication supersedes live evidence regardless of whether that ID appears; a fresh resolution can then consult the updated dataset and, if needed, verify live again. Dataset records with deleted or recycled lifecycle evidence are never overridden by API visibility. Not-found, malformed/incomplete, inaccessible, and ambiguous results remain errors; the app never selects the first of several IDs. Date Manager keeps the page summary concise and puts an allowlisted resolution reason in the CSV `Message` field.

Entries are isolated by Brightspace origin and OAuth client ID inside the selected `MONGODB_URL` database. Changing tenant/client creates a separate namespace. Use one installation per tenant and restrict database access. Dataset access may expose org-unit names/codes across the tenant to the Service User; use this feature only where that directory access is appropriate for the installation's administrators. The directory contains no course content or user enrollment data.

If MongoDB is unavailable during a directory read, preparation stops instead of guessing. If saving a live lookup fails, that job can still use the verified API response; a sanitized server event records the cache-write failure. Job checkpoint failures retain the existing job safety behavior. This feature does not itself fix a MongoDB connectivity outage.

## Setup on Render

1. Deploy the updated source and lockfile with Node.js 22 (`npm ci`, then `npm start`).
2. Confirm the existing OAuth scopes include **`datasets:bds:read`**. Legacy `datahub:dataexports:read` alone does not cover the modern dataset routes used here. Keep the existing orgstructure/copy/date scopes.
3. Give the OAuth **Service User** permission to access Brightspace Data Sets/Data Hub and download the Organizational Units dataset. Scopes alone are insufficient. Confirm dataset generation is enabled and extracts exist. Existing org-unit access remains necessary for live misses and actual jobs.
4. No extra settings are required with the defaults. Optional settings are listed below.
5. Run a manual refresh in **Render → service → Shell** after the Service User is ready:

```sh
node scripts/sync-org-units.js
node scripts/org-unit-cache-report.js
```

The first command downloads datasets and updates only the app directory in MongoDB; it does not copy courses or change Brightspace. It honors the shared rate gate and sync lease. If a scheduled sync is already running, it reports `not_due_or_running`. `already_current` means there is no unprocessed eligible extract, even for a manual run. Manual sync checks immediately; it does not force repeated downloads of known files.

The status command prints readiness, snapshot dates, imported row/extract counts, next run and sanitized failure code/HTTP status. These diagnostics are server-only. `syncMode` identifies the last published import as `full` or `differential`. `importedRows` and `extracts` describe files processed in that run, not cumulative totals or unique active courses; `fullRows` counts every validated row in the full extract, including excluded types and deletion records.

| Optional variable | Default | Meaning |
| --- | --- | --- |
| `ORG_UNIT_DATASET_SYNC_ENABLED` | `true` | Set `false` to stop automatic imports. Persistent lookups and live-miss caching still work. Manual sync remains available. |
| `ORG_UNIT_DATASET_SYNC_HOUR_UTC` | `6` | Integer 0–23; UTC hour for the daily run. |
| `ORG_UNIT_DATASET_SCHEMA_ID` | Auto-detected | Use the schema's `SchemaId` from `GET /d2l/api/lp/{version}/datasets/bds` if name-based discovery cannot identify Organizational Units. Do not use its PluginId. |

All three use ordinary server configuration, not new secrets. Dataset routes require LP 1.49+; the app's default LP 1.53 meets this minimum if supported by the tenant.

## Storage and operational limits

Collections are `org_resolution_units` (staged/published supported org-unit and lifecycle snapshots), `org_resolution_created` (durable confirmed-creation overlay), `org_resolution_live` (live exact-code results), and `org_resolution_state` (schedule/lease/status). The app creates indexes for namespace/generation/code and unique namespace/generation/ID, plus namespace/ID and namespace/code overlay indexes. One document per supported org unit avoids a single giant MongoDB document. To preserve atomic publication without requiring MongoDB transactions, an incremental run copies the supported lifecycle directory into a staging generation in 500-record batches, then applies each differential there with bounded writes and type-transition removals. The extract ledger is capped at 10,000 entries; a newer full resets it.

Files stream to a private temporary directory and are deleted on completion or handled failure. Limits: 256 MiB compressed download, 512 MiB uncompressed CSV, 1,000,000 rows per extract, one CSV per ZIP, 10 minutes per download/parse, 500-row writes. A tenant exceeding a limit requires an intentional capacity review; it never publishes a truncated directory.

Old generations are retained for at least 24 hours so concurrent lookups can finish, and are removed after later successful imports. Handled failed generations are removed immediately; process-crash staging is removed by subsequent cleanup. A sync/schema version change requires a complete authoritative full rebuild before a lifecycle-aware generation can publish. Older extract ledgers are used for continuity checks, so an expired differential history blocks migration until a suitable full is available. The previous generation remains published if rebuild fails. The existing cleanup retains generations needed by readers and removes obsolete generations later. Live overlays predating a successful publication are invalidated. Allow room for the active snapshot, staging, retained generations and indexes **in addition to jobs**. A test-tenant inspection measured 26,393 published rows, of which 10,023 were non-deleted Offerings or Source Courses; retained lifecycle evidence increases the set of supported rows and storage use, which must be measured for the tenant before deployment. These values are tenant-specific, not capacity or throughput promises. Lifecycle records increase persistent storage and differential staging copies; actual capacity depends on index/job size and workload.

## Acceptance check

Run a small codes-only CSV in each tool after a successful sync, then repeat it as a new job. Directory hits should add no `GET .../orgstructure/` requests to `node scripts/api-cost-report.js`; Date Manager's course/activity requests are still expected. Test one ID/code mismatch and an unknown code: the mismatch must be excluded/reported and the unknown code must be resolved live or reported missing. Job preparation timing is available through `node scripts/job-performance-report.js`.

Automated tests cover warm/missing/ambiguous codes, tool integration, batching, namespace isolation, lease fencing, full/differential ordering, renames/deletes, corrupt ZIPs and failed-import preservation. Live tenant dataset access, extract compatibility, storage capacity and throughput must be verified after deployment.

## Troubleshooting

- `DATASET_SCHEMA_NOT_FOUND`: the dataset listing succeeded but no matching schema was identified. Run `node scripts/sync-org-units.js --list-datasets` in Render Shell. This prints schema IDs, full/differential names and availability flags only. It makes metadata GET requests (plus normal rate-limit accounting), without downloading/importing data. Set `ORG_UNIT_DATASET_SCHEMA_ID` to the **Organizational Units** row's schema ID if the name differs; do not choose Ancestors or Descendants. If the dataset is absent, check Service User dataset visibility and tenant Data Hub configuration.
- `DATASET_SCHEMA_AMBIGUOUS`: more than one name matched; select the intended schema explicitly.
- `DATASET_FULL_UNAVAILABLE` / `DATASET_EXTRACT_LINK_MISSING`: the selected schema lacks full-plugin metadata or its extract link. Check dataset availability/permissions; the importer does not guess a download URL.
- HTTP 401/403: check scope, Service User permissions and dataset download quota. Failures retry in one hour; current mappings remain usable.
- `DATASET_FULL_MISSING` / `DATASET_VERSION_MISMATCH`: initial setup/rebuild needs a compatible full plus newer differentials.
- `DATASET_HISTORY_UNAVAILABLE` / `DATASET_HISTORY_CHANGED`: the saved continuation point has expired, a rebuild would lose known changes, or an older unprocessed differential appeared. Wait for a new full covering that history. The current directory remains published; do not delete it to bypass this protection.
- `DATASET_HISTORY_LIMIT`: the 10,000-entry ledger needs a new full baseline.
- `DATASET_TOO_LARGE` or `DATASET_ROW_LIMIT`: review tenant size and hosting/storage capacity.
- `RESOLUTION_LEASE_LOST`: another run took over after a timeout; the losing run cannot publish. Retry after the active import finishes.
- `org_directory_sync_failed`, `resolution_cache_write_failed`, `job_request_failed`, or `job_worker_failed` in Render logs: events include sanitized error class/code and HTTP status, with job ID where available. They omit credentials, raw exception messages and download links. A generic UI storage error should now have a corresponding server event to investigate.

Row-validation diagnostics include only the field name, reason, one-based data-record number (excluding the CSV header), and Full/Differential extract type. No raw row values are logged. Empty descriptive Type labels are retained; actual course type/access enforcement remains with the existing tool checks and Brightspace. Boolean whitespace is ignored, but unknown deletion flags still abort the import.

The directory retains lifecycle evidence for Course Offerings, Source Courses, Course Templates, and Departments identified by the configured type ID. MongoDB supports batched current-only resolution and duplicate discovery across all four types. Strict code resolution is globally unique: one current Course Offering plus one current Source Course, or one current Department plus one current Course Template, is ambiguous. A known recycled/deleted record does not create current ambiguity; unknown lifecycle does. A caller can identify an exact Org Unit ID through MongoDB, with existing type validation retained. Department identification uses numeric `Type.Id` matched to `BS_STD_DEPARTMENT_TYPE_ID`, never a customizable type name or `Type.Code`. The [Org Structure API](https://docs.valence.desire2learn.com/res/orgunit.html) returns paged OrgUnitProperties but does not document deletion or recycling lifecycle fields in that response, so each API match must reconcile by Org Unit ID to trustworthy dataset or creation evidence. An unclassified live match returns `CODE_STATUS_UNKNOWN`; it is not treated as current or cached as a reusable result. Successful lifecycle-backed live results are reused until publication invalidates them. Genuine ambiguity is never resolved by selecting the first ID. Reports distinguish missing codes from multiple live matches. To compare both sources without changing mappings, run `node scripts/sync-org-units.js --check-code YOUR_CODE`. This server-only diagnostic shows matching IDs, codes and types; it does not submit copy jobs.

## Source Course creation overlay and migration

Directory sync version 7 adds retained lifecycle evidence for all supported types. Existing version 6 and older installations automatically require an authoritative full rebuild, even when no newer differential exists. The configured Department type ID is saved with each published generation; a configuration change also requires an authoritative full rebuild so the generation is filtered using the new identity. If the setting is missing or invalid, ordinary course resolution remains available, Department records are not imported, and Department-specific identification reports that configuration is unavailable. The existing ledger continuity checks, lease fencing, staged generation publication and retention rules still apply. If the full or necessary continuity history is unavailable, the previous published generation remains active.

Successful Bulk Source Course Creator rows are stored separately in `org_resolution_created`, keyed by tenant namespace and returned Org Unit ID, with name, code, normalized `Source Course` type, creation time, and job/row provenance. Upserts are idempotent. The resolver merges active creation records with dataset and live exact-code records; this exposes newly created Source Courses before the next nightly import while retaining ambiguity detection. A local creation record never proves code uniqueness. Creator duplicate checks batch distinct source codes through the shared MongoDB lookup and use exact-code Brightspace reads only when the shared freshness/safety rules require them. One or more current Source Courses cause a skip; deleted/recycled-only results can be reused; cross-type current matches and unknown lifecycle are rejected safely. Deactivated Source Courses remain current because `IsActive` does not determine lifecycle.

After confirmed Source Course creation workers drain, the Creator reconciles once per affected Course Template using the saved Department parent set. It POSTs every intended Department relationship, then removes only the positively identified Root Organization parent. Brightspace testing confirmed that adding an existing Department relationship returns HTTP 200, so normal reconciliation has no direct-parent GET. The actual Root ID is resolved and persisted once per job. Each parent mutation has a durable intent and outcome; if a response is uncertain, restart recovery uses a read-only direct-parent lookup before deciding whether to retry. A creation cancellation still reconciles templates that received a submitted or uncertain creation POST. The shared tenant worker lease serializes jobs so another workflow job cannot interleave changes to the same template. Parent outcomes are stored once per template and copied into CSV rows at report time.

When a dataset record newer than the creation timestamp includes the ID, it supersedes the overlay and the dataset becomes authoritative (including rename or type changes). A sufficiently newer authoritative generation that omits the ID supersedes the creation record as a deletion/type-transition signal. Older extracts leave the creation record active. If the Brightspace POST succeeded but the overlay upsert failed, the workflow keeps the confirmed Org Unit ID and retries only the database upsert during recovery; the creation POST is never repeated.

Lifecycle policy: `current` requires `IsDeleted=false`, empty `DeletedDate`, and empty `RecycledDate`; `recycled` means `RecycledDate` is populated; `deleted` means deletion evidence exists without a recycling indicator; missing required status is `unknown`. `IsActive=false` does not affect lifecycle. Differential records retain supported IDs with updated lifecycle evidence and remove IDs only when they change to an unsupported type. Version 7 forces an authoritative full rebuild even when no newer extracts exist and invalidates live-cache results saved before publication. If the full or required continuity history is unavailable, the old generation remains in use and the sync reports the issue; operators should wait for a suitable full rather than delete collections. Run the sync after deploying before retrying affected CSV jobs.

## Header sync button

A small sync icon to the right of the Language selector requests a directory refresh from an authorized LTI session. Its tooltip and screen-reader name are translated into English, Spanish and Portuguese. The request is saved in MongoDB and starts in the background without navigation or resetting CSV/date/component fields. A brief message confirms the request, an existing run, or a request error; it does not claim the import has completed. Detailed sync results stay in server logs and `org-unit-cache-report.js`.

The protected POST `/org-directory/sync` requires a signed, expiring ticket bound to the validated LTI session, user and configured deployment. It follows the app’s existing deployment-access policy and adds no separate administrator role. The icon is absent outside an authorized session. Concurrent imports are prevented by the existing database lease, and user requests are limited to one per minute per directory. Manual requests work even when automatic scheduling is disabled. A lost HTTP response can be retried without launching duplicate simultaneous imports. The button uses the same incremental/full policy as the server command.
