# Shared org-code directory

Course Copy, Source Deployer and Date Manager now share a persistent org-code → ID directory in the app's existing MongoDB database. No new database, Redis service, CSV column or end-user control is required.

## What happens on upload

1. IDs without codes bypass code resolution entirely.
2. The app deduplicates supplied codes and queries MongoDB in batches of 500. Known codes need no Brightspace lookup.
3. Missing codes use the existing `orgstructure/?exactOrgUnitCode=...` API, with up to eight mapping workers and the shared API rate limits. All returned pages are checked for ambiguity (bounded to 100 pages / 5,000 matches). Successful results are saved for later jobs; repeated codes within the current job share one lookup promise. Not-found results are not cached permanently.
4. If both ID and code are supplied, the resolved ID must match. Ambiguous codes and mismatches are rejected, never guessed. Existing duplicate, self-copy and conflict checks remain.

Course Copy and Source Deployer exclude invalid rows and retain them in reports. Date Manager retains its existing requirement that all courses pass validation before application. Date Manager still reads current course details and activities; Source Deployer still performs its execution-time checks before deactivation/deployment. Copy submissions and date updates remain at four workers. The directory does not grant API permissions or change submission/retry behavior.

## Nightly refresh

The running app checks whether a refresh is due at startup and every minute. The default schedule is **06:00 UTC (03:00 Brasília)**. A missed run is picked up when the service next starts; a sleeping or stopped server cannot run a timer. Configure the hour after your tenant's dataset generation window.

The importer discovers the **Organizational Units** Brightspace Data Set, downloads the newest full extract and the available newer differential extracts in chronological order, then builds a separate MongoDB generation. It publishes that generation atomically only after every file has been downloaded, parsed, validated and saved. Failed imports leave the previous generation usable and retry after one hour. A database lease prevents overlapping scheduled/manual imports across app instances. Restarted imports rebuild staging rather than publishing partial data.

Brightspace's dataset API supplies opaque extract/download links; the app follows those links rather than constructing filenames. It handles paginated metadata and signed HTTPS redirects. OAuth authorization is sent only to the initial tenant API URL, never to an external download host. See [D2L's dataset API](https://docs.valence.desire2learn.com/res/dataExport.html#brightspace-data-sets).

The imported fields are OrgUnitId, Code, Name, Type and deletion state. Full snapshots remove records no longer present; differentials apply code changes and deletion records. All org-unit types are retained so duplicate codes remain detectable. Source Course is not treated as Course Template. These fields come from the [Organizational Units dataset](https://community.d2l.com/brightspace/kb/articles/4529-organizational-units-data-sets).

Imports reject missing required headers, duplicate IDs within an extract, incompatible dataset versions, missing full extracts, invalid ZIP/CRC, and gaps longer than 36 hours between a full/differential and the next differential. This daily-granularity gap guard cannot prove that every hourly differential exists. Dataset availability/freshness must still be monitored. No new dataset is generated by the app; it consumes published extracts.

## Freshness and isolation

**A cached match reflects the latest imported dataset or successful live lookup, not a live verification.** If an existing code is renamed or reassigned after that point, the cache can remain stale until the next refresh. ID+code matching uses that same directory. Use IDs alone when identity must not depend on a mutable code. Changing permissions is still enforced by Brightspace when processing requests; directory membership is not an access grant.

Live lookups newer than the full snapshot are retained until an authoritative newer full or differential supersedes them. Renames/deletions in a newer differential also invalidate older live matches. Not-found/ambiguous rows remain errors; the app never selects the first of several IDs.

Entries are isolated by Brightspace origin and OAuth client ID inside the selected `MONGODB_URL` database. Changing tenant/client creates a separate namespace. Use one installation per tenant and restrict database access. Dataset access may expose org-unit names/codes across the tenant to the Service User; use this feature only where that directory access is appropriate for the installation's administrators. The directory contains no course content or user enrollment data.

If MongoDB is unavailable during a directory read, preparation stops instead of guessing. If saving a live lookup fails, that job can still use the verified API response; a sanitized server event records the cache-write failure. Job checkpoint failures retain the existing job safety behavior. This feature does not itself fix a MongoDB connectivity outage.

## Setup on Render

1. Deploy the updated source and lockfile with Node.js 22 (`npm ci`, then `npm start`).
2. Confirm the existing OAuth scopes include **`datasets:bds:read`**. Legacy `datahub:dataexports:read` alone does not cover the modern dataset routes used here. Keep the existing orgstructure/copy/date scopes.
3. Give the OAuth **Service User** permission to access Brightspace Data Sets/Data Hub and download the Organizational Units dataset. Scopes alone are insufficient. Confirm dataset generation is enabled and extracts exist. Existing org-unit access remains necessary for live misses and actual jobs.
4. No extra settings are required with the defaults. Optional settings are listed below.
5. Run a manual refresh in **Render → service → Shell** after the Service User is ready:

```sh
node scripts/sync-org-units.js
node scripts/org-unit-cache-report.js
```

The first command downloads datasets and updates only the app directory in MongoDB; it does not copy courses or change Brightspace. It honors the shared rate gate and sync lease. If a scheduled sync is already running, it reports `not_due_or_running`. `already_current` means the available extract timestamp is already imported, even for a manual run.

The status command prints readiness, snapshot dates, imported row/extract counts, next run and sanitized failure code/HTTP status. These diagnostics are server-only. `importedRows` includes differential rows, so it is not the number of distinct active courses; `fullRows` includes every org-unit type and deletion record in the full extract.

| Optional variable | Default | Meaning |
| --- | --- | --- |
| `ORG_UNIT_DATASET_SYNC_ENABLED` | `true` | Set `false` to stop automatic imports. Persistent lookups and live-miss caching still work. Manual sync remains available. |
| `ORG_UNIT_DATASET_SYNC_HOUR_UTC` | `6` | Integer 0–23; UTC hour for the daily run. |
| `ORG_UNIT_DATASET_SCHEMA_ID` | Auto-detected | Use the schema's `SchemaId` from `GET /d2l/api/lp/{version}/datasets/bds` if name-based discovery cannot identify Organizational Units. Do not use its PluginId. |

All three use ordinary server configuration, not new secrets. Dataset routes require LP 1.49+; the app's default LP 1.53 meets this minimum if supported by the tenant.

## Storage and operational limits

Collections are `org_resolution_units` (staged/published snapshots), `org_resolution_live` (live misses), and `org_resolution_state` (schedule/lease/status). The app creates indexes for namespace/generation/code and unique namespace/generation/ID. One document per org unit avoids a single giant MongoDB document.

Files stream to a private temporary directory and are deleted on completion or handled failure. Limits: 256 MiB compressed download, 512 MiB uncompressed CSV, 1,000,000 rows per extract, one CSV per ZIP, 10 minutes per download/parse, 500-row writes. A tenant exceeding a limit requires an intentional capacity review; it never publishes a truncated directory.

Old generations are retained for at least 24 hours so concurrent lookups can finish, and are removed after later successful imports. Handled failed generations are removed immediately; process-crash staging is removed by subsequent cleanup. Live overlays covered by a newer full are removed. Allow room for the active snapshot, staging, retained generations and indexes **in addition to jobs**. A large directory can exceed Atlas M0's 512 MB capacity. Check Atlas storage before importing a very large tenant; free-tier suitability depends on actual directory/job size, not the 5,000 rows in one upload.

## Acceptance check

Run a small codes-only CSV in each tool after a successful sync, then repeat it as a new job. Directory hits should add no `GET .../orgstructure/` requests to `node scripts/api-cost-report.js`; Date Manager's course/activity requests are still expected. Test one ID/code mismatch and an unknown code: the mismatch must be excluded/reported and the unknown code must be resolved live or reported missing. Job preparation timing is available through `node scripts/job-performance-report.js`.

Automated tests cover warm/missing/ambiguous codes, tool integration, batching, namespace isolation, lease fencing, full/differential ordering, renames/deletes, corrupt ZIPs and failed-import preservation. Live tenant dataset access, extract compatibility, storage capacity and throughput must be verified after deployment.

## Troubleshooting

- `DATASET_SCHEMA_NOT_FOUND`: the dataset listing succeeded but no matching schema was identified. Run `node scripts/sync-org-units.js --list-datasets` in Render Shell. This prints schema IDs, full/differential names and availability flags only. It makes metadata GET requests (plus normal rate-limit accounting), without downloading/importing data. Set `ORG_UNIT_DATASET_SCHEMA_ID` to the **Organizational Units** row's schema ID if the name differs; do not choose Ancestors or Descendants. If the dataset is absent, check Service User dataset visibility and tenant Data Hub configuration.
- `DATASET_SCHEMA_AMBIGUOUS`: more than one name matched; select the intended schema explicitly.
- `DATASET_FULL_UNAVAILABLE` / `DATASET_EXTRACT_LINK_MISSING`: the selected schema lacks full-plugin metadata or its extract link. Check dataset availability/permissions; the importer does not guess a download URL.
- HTTP 401/403: check scope, Service User permissions and dataset download quota. Failures retry in one hour; current mappings remain usable.
- `DATASET_FULL_MISSING`, `DATASET_DIFFERENTIAL_GAP`, or `DATASET_VERSION_MISMATCH`: check Data Hub availability; wait for a complete compatible full/differential sequence. No partial import is published.
- `DATASET_TOO_LARGE` or `DATASET_ROW_LIMIT`: review tenant size and hosting/storage capacity.
- `RESOLUTION_LEASE_LOST`: another run took over after a timeout; the losing run cannot publish. Retry after the active import finishes.
- `org_directory_sync_failed`, `resolution_cache_write_failed`, `job_request_failed`, or `job_worker_failed` in Render logs: events include sanitized error class/code and HTTP status, with job ID where available. They omit credentials, raw exception messages and download links. A generic UI storage error should now have a corresponding server event to investigate.

Row-validation diagnostics include only the field name, reason, one-based data-record number (excluding the CSV header), and Full/Differential extract type. No raw row values are logged. Empty descriptive Type labels are retained; actual course type/access enforcement remains with the existing tool checks and Brightspace. Boolean whitespace is ignored, but unknown deletion flags still abort the import.
